# mobile-release

A Go CLI that builds and distributes **Flutter**, **Expo**, **Kotlin
Multiplatform** and **native** apps (Gradle + Xcode, including projects
generated by [jirau](https://github.com/lucaswilliameufrasio/jirau)). Each app
only keeps a secret-free `release.toml`; the CLI asks for whatever is missing,
stores credentials once in your secret store and runs the same flow locally or
in CI.

- **Guided:** `init` detects the project, `setup` asks for each missing
  credential (what it is and where to get it), `doctor` shows what is ready,
  `deploy` confirms before publishing.
- **No Fastfile in the app:** the fastlane lanes are embedded in the binary,
  with pinned versions (`Gemfile.lock`).
- **Credentials are never shown:** values travel through the environment or
  stdin, files become `0600` temporary files, and summaries only show
  name → source.

## Installation

```bash
go install github.com/lucaswilliameufrasio/mobile-release/v2/cmd/mobile-release@latest
```

Requires Ruby ≥ 3.2 with Bundler (fastlane gems are kept in the user cache)
and your project's tools (Flutter, Node, JDK, Xcode). `mobile-release doctor`
lists what is missing and how to install it.

## Quick start

```bash
cd my-app
mobile-release init      # detects type, ids and .env files; asks for environments and destinations
mobile-release setup     # asks for missing credentials and saves them in the chosen store
mobile-release doctor    # tools, configuration and credentials per environment
mobile-release deploy    # pick environment and platform, review the plan, confirm and publish
```

`deploy -dry-run` prints every command without building or publishing.

To set up a whole project at once, `mobile-release adopt` runs `init` when
needed, adds a managed Makefile block that pins the CLI version
(`make release-install`, `release-setup`, `release-doctor`, `deploy`,
`deploy-dry-run`, `release-qa`), ignores `dist/` and, with `-workflow`, adds a
manual release workflow pinned to the release's commit. It shows the plan,
asks before writing and never overwrites: hand-written targets or an existing
workflow are reported and left alone.

`mobile-release migrate` brings `release.toml` to the current schema: schema 1
files are rewritten (comments cannot be kept), and in schema 2 files keys equal
to their default are removed line by line, keeping comments, unless a comment
documents them. It refuses any result that would change the effective
configuration, lists what needs your attention (e.g. a bundle id that schema 1
never had) and asks before writing.

`mobile-release upgrade` moves to the latest release of the installed major
version: it shows the installed and pinned versions and the release notes in
between, refreshes the managed Makefile block and the release workflow pins
(commit and version) after asking, and installs the new CLI only when you
confirm (or pass `-install`). `-to vX.Y.Z` picks a version; `-dry-run` only
prints. New major versions change the module path, so they are announced but
never applied automatically.
`mobile-release qa` builds an APK and a simulator app without release signing.

## release.toml

```toml
schema_version = 2

[project]
type = "flutter"            # flutter | expo | kmp | native
# preset = "jirau"          # native project generated by jirau (detected from jirau.toml)

[app]
name = "Shop"

[android]
package_name = "com.example.shop"
# signing = "project"       # default "injected": the CLI injects the keystore into Gradle

[ios]
bundle_id = "com.example.shop"
team_id = "ABCDE12345"
signing = "match"           # automatic (App Store Connect key) | match | manual

[environments.staging]
env_file = ".env"
defines = { APP_COMMIT = "{commit}" }
destinations = ["firebase"]

[environments.staging.firebase]
android_app_id = "1:123:android:abc"
ios_app_id = "1:123:ios:def"
groups = ["internal-testers"]

[environments.production]
env_file = ".env.production"
defines = { APP_VARIANT = "production" }
build_number = "store"
destinations = ["play", "testflight"]
```

| Field | Values |
| --- | --- |
| `destinations` | `firebase` (APK + ad-hoc IPA), `play` (AAB), `testflight`, `app-store` (submit for review), `ota` (Expo), `artifacts` (build into `dist/` only) |
| `build_number` | `timestamp` (UTC `yyDDDHHMM`, default), `store` (latest in the store + 1), `project` (keep the project's) or an integer |
| `env_file` | Flutter: `--dart-define-from-file`; others: build environment variables (e.g. `EXPO_PUBLIC_*`) |
| `defines` | Flutter: `--dart-define`; others: environment. Supports `{commit}`, `{build_number}` and `{env}` |
| `[prepare]` | `all`, `android`, `ios`: shell commands run before the builds, with the environment's defines |
| `[environments.<name>.prepare]` | same keys, only for that environment, after the global ones (e.g. per-environment app icons) |
| `confirm` | environments with `play`, `testflight` or `app-store` require typing the environment name by default |

Unknown keys are errors (typos never become silent defaults) and validation
reports every problem at once. `schema_version = 1` files keep working as an
`internal` environment. See [`examples/`](examples/) for Flutter, Expo, KMP,
native and jirau projects.

### How each type builds

| Type | Android | iOS (before the archive) |
| --- | --- | --- |
| Flutter | `flutter build apk/appbundle` with defines, obfuscation and `--build-number` | `flutter build ios --config-only` |
| Expo | installs dependencies (pnpm/yarn/bun/npm from the lockfile), `expo prebuild`, Gradle | — |
| KMP | `apk_task`/`aab_task` | `iosApp` project |
| Native | `./gradlew assembleRelease/bundleRelease` in `android/` | `xcodegen` when a spec is set |
| jirau | Gradle (the Rust core is built in `preBuild`) | `scripts/build-ios-ffi.sh release` + `xcodegen generate` |

Archiving and exporting the IPA is shared by every type (fastlane `gym`), so
every type gets the same signing options. The build number reaches Android
through `android.injected.version.code` and iOS through
`CURRENT_PROJECT_VERSION` (Flutter uses its own mechanisms). Android release
signing uses the Android Gradle Plugin's injected signing properties through
`ORG_GRADLE_PROJECT_*` variables: the app needs no `key.properties` and
passwords never appear as arguments.

## Credentials

The CLI derives which credentials each deploy needs from its destinations,
signing and build number strategy: you never need to know variable names.
Values can be shared by every environment (e.g. the upload keystore) or apply
to one (e.g. a staging Firebase service account).

Each credential is looked up in the stores in order; the first one that has it
wins:

1. `keychain` — macOS Keychain (service `mobile-release`).
2. Custom stores (below), in alphabetical order.
3. `bitwarden` — Bitwarden CLI. During `setup` you pick the item (only names
   are shown) and the choice is remembered by item id.
4. `env` — `MOBILE_RELEASE_*` variables (CI).

### Personal configuration

Lives in `~/.config/mobile-release/config.toml` (Linux) or
`~/Library/Application Support/mobile-release/config.toml` (macOS), never in
the project:

```toml
# Optional: explicit order
order = ["keychain", "my-vault", "bitwarden", "env"]
default_store = "keychain"

# A tool that runs a command with secrets in its environment
# ("<tool> run -- <command>"). The CLI re-runs itself inside it.
[stores.my-vault]
type = "exec"
command = ["my-vault", "run", "--env", "{env}", "--"]
env_names = { production = "prd" }          # the environment's name in the tool
# vars = { "android.keystore" = "ANDROID_KEYSTORE_BASE64" }  # if names differ

# Or a per-key read/write tool (1Password, pass, ...)
[stores.op]
type = "command"
get = ["op", "read", "op://Private/{key}"]  # prints the value
# set = [...]                                # receives the value on stdin
```

Placeholders: `{app}`, `{env}`, `{id}` and `{key}` (`app/env/id`). Files are
stored base64-encoded.

## Agents (MCP)

`mobile-release mcp` serves the CLI to agents over the Model Context Protocol
(stdio):

```bash
claude mcp add mobile-release -- mobile-release mcp     # Claude Code
```

```json
{ "mcpServers": { "mobile-release": { "command": "mobile-release", "args": ["mcp"] } } }
```

| Tool | What it does |
| --- | --- |
| `environments` | environments, destinations and build number strategy of a project |
| `doctor` | tools, configuration and credentials (names and stores, never values) |
| `plan` | dry run of a release: every command, nothing built or published |
| `qa` | local APK + simulator build, nothing published |
| `adopt` | sets a project up (see above), **always after asking the user** |
| `upgrade` | moves the project pins to the latest release, **always after asking the user**; returns the CLI install command |
| `migrate` | brings `release.toml` to the current schema, **always after asking the user** |
| `deploy` | builds and publishes, **always after asking the user** |

`deploy` runs the plan and asks the user through MCP elicitation, showing that
plan; store destinations also require typing the environment name. Nothing is
published on a decline, a cancel, a mismatched name, or when the client cannot
ask, in which case the plan and the terminal command are returned instead. The
confirmation is bound to the request that asked for it, and every tool runs the
CLI itself, so agents get the same checks and credential stores as a terminal.
Credentials are never returned to the agent: when some are missing, run
`mobile-release setup` in a terminal.

## CI

The reusable workflow installs the CLI and runs `deploy` without prompts
(`-yes`):

```yaml
jobs:
  release:
    uses: lucaswilliameufrasio/mobile-release/.github/workflows/reusable-release.yml@v2.0.1
    with:
      environment: staging
      platform: android
      runner: ubuntu-latest           # iOS needs macOS
      flutter-version-file: pubspec.yaml
    secrets: inherit
```

Accepted secrets: `MOBILE_RELEASE_ANDROID_KEYSTORE_BASE64`,
`MOBILE_RELEASE_ANDROID_KEYSTORE_PASSWORD`, `MOBILE_RELEASE_ANDROID_KEY_ALIAS`,
`MOBILE_RELEASE_ANDROID_KEY_PASSWORD`, `MOBILE_RELEASE_GOOGLE_PLAY_JSON_BASE64`,
`MOBILE_RELEASE_FIREBASE_SERVICE_ACCOUNT_BASE64`,
`MOBILE_RELEASE_APP_STORE_KEY_ID`, `MOBILE_RELEASE_APP_STORE_ISSUER_ID`,
`MOBILE_RELEASE_APP_STORE_PRIVATE_KEY_BASE64`, `MOBILE_RELEASE_MATCH_GIT_URL`,
`MOBILE_RELEASE_MATCH_PASSWORD`, `MOBILE_RELEASE_MATCH_SSH_KEY` and
`MOBILE_RELEASE_EXPO_TOKEN`. When something is missing, the error lists exactly
which ones.

## Security

- No secret goes into `release.toml`, process arguments or logs; printed
  commands only show the **names** of the variables passed.
- OTA commands only receive the Expo token (`eas` mode), never signing or
  store keys.
- match runs read-only; to create certificates, run it deliberately with
  `MOBILE_RELEASE_MATCH_READONLY=false`.
- Never commit `.p8`, `.p12`, provisioning profiles, service accounts or
  keystores.
